# Claude Code Elephant-Goldfish Model (EGM) Reference

Source video: https://www.youtube.com/watch?v=xxf6D9jynFw

## Purpose

Chapter-complete playbook for Google's Elephant-Goldfish Model (EGM): a spec-driven Claude Code workflow that plans a feature, has context-free subagents attack the plan, and only then builds. Covers install, the five commands (bootstrap, brainstorm, draft, review, drift report), and when it is worth the overhead.

This guide focuses on:
- Separating the agent that plans (Elephant) from agents that critique (Goldfish)
- Mapping an existing codebase so agents can read per-folder rules
- Reviewing a plan before any code is written, then auditing code against it later

## Chapter-by-chapter reference

### 0:00 Intro

- **Concept:** EGM is Google's approach to vetting an agent's plan before it builds, instead of discovering problems afterward.
- **Prerequisites:** None.
- **When to use:** Deciding whether to watch/adopt; the claim is it caught a real bug that a regular check missed.
- **Example:** Adding a feature to an existing app and wanting the plan challenged first.

### 0:47 What It Is

- **Concept:** Google's version of spec-driven development: write the complete plan first, then have the agent build against it. Based on Dave Rensin's article; free on Google's GitHub. Uses multiple agents and skills so the plan has no gaps and the implementing agent never has to guess. Output is a plan plus a build/test checklist.
- **Prerequisites:** Claude Code (or Codex/other supported agent).
- **When to use:** Features where ambiguity during implementation is costly.
- **Example:** A plan that states what to build, how to test it, and when the feature counts as done.

### 1:43 Elephant vs Goldfish

- **Concept:** Two roles, plus you as the third.
  - **Elephant:** the workflow that remembers everything (project history, structure, purpose). Talks the idea through with you, probes weak points, writes the planning files.
  - **Goldfish:** subagents with zero context. They see only the plan and the code, never your chat, so nothing you said can bias them.
  - **You:** make final calls. Reviews intentionally produce many notes; keep what is useful, drop the rest.
- Goldfish review from different angles: simpler alternative or existing code that already does it; readability for someone who knows nothing about the app; concurrency/multi-user problems; clarity enough to implement without assumptions; plan structure/writing.
- Reviews use written rules (checklists of what a good plan contains). One orchestrating subagent launches the others and merges their output into a single report, which keeps the main agent's context small.
- **Prerequisites:** Understanding that subagents start with clean context.
- **When to use:** Any time you suspect the planning agent would just agree with itself.
- **Example:** Chat-trained planner approves its own design; a fresh subagent flags a missing edge case.

### 3:02 Why Not Plan Mode

- **Concept:** Plan mode usually yields a plan with gaps that surface later, forcing rework. It also happens in the same chat, so the "review" is the model agreeing with itself (models tend to defend their own assumptions and go along with the user). EGM adds context isolation plus a user checkpoint at every stage. After building, a drift check compares plan to code.
- **Prerequisites:** None.
- **When to use:** Large features; not a replacement for plan mode on small tasks.
- **Example:** Compare a plan-mode plan to an EGM concept brief for the same feature and note what the Goldfish added.

### 4:54 Install

- **Concept:** Install via the repo's per-agent command (Claude Code, Codex, others), or paste "install" + the repo link into your agent. Installation creates three folders under `.claude/`: `agents/` (the Goldfish), `EGM/` (a full copy of the repo), `skills/` (the Elephant steps; key ones are brainstorming and review). It also writes instructions into `CLAUDE.md`.
- **Prerequisites:** Network access to GitHub; project with Claude Code configured.
- **When to use:** Once per project.
- **Example:**
  - Prompt: `install https://github.com/google/elephant-goldfish-model`
  - Verify `.claude/agents`, `.claude/EGM`, `.claude/skills` exist.

### 6:07 Fixing CLAUDE.md

- **Concept:** The generated `CLAUDE.md` may contain a line saying subagents cannot spawn subagents. That was true in older Claude Code versions; the agent wrote it from memory, not from the repo. Newer versions allow nesting, and the review depends on it. Tell Claude the line is wrong, have it test, and fix the line. The per-agent install command avoids the conflict.
- **Prerequisites:** Installed EGM; a current Claude Code version.
- **When to use:** Immediately after install; recheck after repo updates (the repo changes often).
- **Example:** Search `CLAUDE.md` for text like "subagents cannot run their own subagents", then ask Claude to verify nesting works and correct it.

### 7:08 Bootstrap

- **Concept:** Run the EGM bootstrap command before the first feature. It walks the app one folder at a time and writes a README per code folder (purpose, contents, how parts connect, rules to follow), and adds a section to the main README. Folders without code (e.g. specs) are skipped. If the app has more than 15 folders, it asks before doing a full mapping because it needs many subagents. Demo result: 28 new READMEs plus an updated root README.
- **Gotcha:** READMEs are written for humans, so Claude Code does not read them on its own. Three fixes:
  1. Add a `CLAUDE.md` next to each README that tells Claude to read it (use `AGENTS.md` for Codex).
  2. Re-run bootstrap with the option that creates those `CLAUDE.md` files up front.
  3. Add a line to the root `CLAUDE.md` telling Claude to read the folder README wherever it works.
  The video used option 1 and confirmed Claude followed them.
- **Prerequisites:** Installed EGM; an existing codebase; token budget for many subagents.
- **When to use:** First run on an existing app, and again if the structure changes a lot.
- **Example:** Run bootstrap on a 28-folder app, then confirm a feature edit loads the relevant folder README.

### 10:18 Brainstorm

- **Concept:** Start the EGM brainstorm command with the feature idea. It inspects existing plans, points out flaws, and asks questions until the problem is clear (more questions if no plan exists). It then proposes a recommended approach and offers two choices: run the Goldfish review, or push back in chat. The Goldfish run launches one subagent that launches six more in the background, each with a clean slate and no chat. Output is a **concept brief** in the project root covering the feature, findings, blockers, and work needed. You may edit it freely.
- **Prerequisites:** Bootstrap done; a feature idea.
- **When to use:** Start of every non-trivial feature.
- **Example:** Seller dashboard page showing which sizes sell, which are out, and when to restock; answer the questions, accept the approach, run the six-agent review, read the concept brief.

### 11:32 Draft

- **Concept:** The draft command turns the concept brief into a design draft, built in parts with your approval after each:
  1. Feature, problem, and scope (what it will and will not do), plus critical user journeys to turn into tests.
  2. Technical plan.
  3. Considered alternatives with pros/cons and why they were not chosen.
  4. Step-by-step development plan.
  The result is saved by feature name in `docs/designs/`. Later build tasks reference these files.
- **Prerequisites:** An approved concept brief.
- **When to use:** After the brief is acceptable.
- **Example:** Approve scope and journeys, then technical plan, then alternatives, then the step list; confirm a file exists in `docs/designs/`.

### 12:42 Review

- **Concept:** The same agent that agreed with you wrote the draft, so run the review command before building. It starts with a **zoom out** subagent (simpler way? something similar already in the app?) and writes a report of serious problems. Then five rounds of Goldfish review follow, each looking from a different angle; the tool numbers them 5 to 9. After each round you get a report, the plan in `docs/designs/` is updated, and you can proceed or request changes. When finished the plan status moves from "under review" to "proposed" and the review is marked complete. Then open a fresh chat and ask the agent to build from that design file.
- **Prerequisites:** A draft in `docs/designs/`.
- **When to use:** Always, before implementation of an EGM plan.
- **Example:** Run review, accept most round reports, push back on one, close the review, `/clear`, then "implement `docs/designs/<feature>.md`".

### 13:50 Drift Report

- **Concept:** After features ship, code drifts from the READMEs. The drift report command asks which area to check, runs subagents over the chosen parts, and reports where the app no longer matches the rules. It can also surface real bugs; in the demo, shop owners could delete sold products although the rule says sold products may only be hidden. You then choose what to fix.
- **Prerequisites:** Bootstrap READMEs (the rules being checked against).
- **When to use:** Periodically, and after large features.
- **Example:** Run drift report across all READMEs, read the findings, fix the delete-vs-hide violation.

### 14:35 When to Use It

- **Concept:** Best for large features where mistakes are expensive; it explores edge cases and options more deeply than other planning methods the creators tried, and its drift check covers the whole app rather than one feature. Not for small fixes an agent can make directly (planning and review just slow them down). It takes longer, which is the trade-off. The creators mention a simplified version of the workflow with less depth (details in their channel resources).
- **Prerequisites:** n/a.
- **When to use:** See the decision table below.
- **Example:** Typo or one-line fix: skip EGM. Multi-table schema change with concurrent users: use EGM.

## Practical implementation checklist

- [ ] Install EGM using the command for your agent
- [ ] Check `CLAUDE.md` for the "subagents cannot spawn subagents" line and correct it
- [ ] Run bootstrap; approve the full mapping if the app has more than 15 folders
- [ ] Make Claude read folder READMEs (per-folder `CLAUDE.md`/`AGENTS.md`, or a root `CLAUDE.md` rule)
- [ ] Brainstorm the feature, answer all questions, run the Goldfish review, read the concept brief
- [ ] Draft the design section by section, approving each
- [ ] Run review through all rounds and close it (status becomes "proposed")
- [ ] Open a fresh chat and build from the `docs/designs/` file
- [ ] Run a drift report periodically

When to use EGM:

| Situation | Use EGM? |
|---|---|
| Large feature, costly if wrong | Yes |
| Concurrency/multi-user behavior at stake | Yes |
| Small fix an agent can do directly | No |
| Quick experiment or throwaway prototype | No |
| Long-lived app needing alignment with documented rules | Yes (drift report) |
